# Column Editing — EARS Specs

## COL-UI (Edit Columns dialog / staging behavior)

- [x] **COL-UI-001**: The system shall stage all column additions, edits, deletions, and reorderings in memory while the Edit Columns dialog is open, without modifying the underlying database file.
- [x] **COL-UI-002**: When the user presses "Add", the system shall prompt for a new column's name, type, and default value, and shall reject invalid names or default values without closing the subdialog.
- [x] **COL-UI-003**: When the user presses "Edit" on an existing column, the system shall allow changing the column's name and default value but not its data type.
- [x] **COL-UI-004**: When the user presses "Delete" on a column, the system shall remove it from the staged column list without immediately modifying the database file.
- [x] **COL-UI-005**: When the user presses "Up" or "Down" on a column, the system shall swap its staged position with the adjacent column's.
- [x] **COL-UI-006**: When the user renames a column that is referenced by a calculated column's formula, the system shall update that formula to use the new name.
- [x] **COL-UI-007**: When the user deletes a column that is referenced by a calculated column's formula, the system shall clear or invalidate that formula's reference to the deleted column.
- [x] **COL-UI-008**: When the Edit Columns dialog is confirmed ("OK"/"Done"), the system shall apply all staged changes to the database in this order: deletions, then index/default changes to surviving columns, then renames, then additions, then calculated-column updates.
- [x] **COL-UI-009**: When the Edit Columns dialog is cancelled, the system shall discard all staged changes and leave the database's column format unmodified.
- [x] **COL-UI-010**: When a column is deleted from the staged list, the system shall renumber the remaining staged columns' positions to a contiguous sequence starting at zero, based on each column's current staged position, regardless of any reordering ("Up"/"Down") performed earlier in the same dialog session.
- [x] **COL-UI-011**: When a column that was added earlier in the same Edit Columns dialog session is deleted before the dialog is confirmed, the system shall apply no change to the database for that column.
- [x] **COL-UI-012**: When a column that was added earlier in the same Edit Columns dialog session is renamed before the dialog is confirmed, the system shall create the column under its final staged name only.
- [x] **COL-UI-013**: When a column is deleted and a new column with the same name is added in the same Edit Columns dialog session, the system shall on confirm delete the original column and create the new column with its default value in every existing data row (no carry-over of the deleted column's data).
- [x] **COL-UI-014**: When column renames staged in one Edit Columns dialog session form a cycle (for example, two columns' names swapped with each other), the system shall apply them such that every column, and every view/sorting/filter/calculation reference to it, ends at its staged final name. Implemented by replaying the renames through unique temporary (underscore-prefixed) names in two passes, so a transient duplicate name can never mis-target a subsequent name-based rename.
- [x] **COL-UI-015**: When every column is deleted in one Edit Columns dialog session and the dialog is confirmed, the system shall return the database to the valid zero-column state (the same state as a newly created file).

## COL-DB (Database schema mutation)

- [x] **COL-DB-001**: When a column is added, the system shall assign it a unique integer ID, reusing the lowest available gap left by a previously-deleted column's ID if one exists.
- [x] **COL-DB-002**: When a column is added, the system shall populate a type-appropriate default value for that column in every existing data row.
- [x] **COL-DB-003**: When a column is added and the "_all" view (the view listing all columns) exists, the system shall register the new column in it at the position specified by the caller.
- [x] **COL-DB-004**: When a column is deleted, the system shall remove it from every view, sorting, and filter that references it, and shall delete its calculation definition if it is a calculated column.
- [x] **COL-DB-005**: When a column is renamed, the system shall update references to it in every view, sorting, filter, and calculation that uses it.
- [x] **COL-DB-006**: When one or more columns have been added, deleted, or renamed, the system shall regenerate the data table's format string to reflect the current column set.
- [x] **COL-DB-007**: When a column is added to an existing (previously-saved) database file and the Edit Columns dialog is saved, the system shall apply the change without crashing — including on files whose view structures carry historical inconsistencies (a missing "_all" view, or view entries referencing columns that no longer exist). Achieved by robustness rather than a single fix: the confirmed real-world crash was the calc-recalc row-ID conflation (COL-DB-010), and the view-structure crashes are closed by `_all` reconciliation (COL-DB-008) and orphan-tolerant view loading (COL-DB-009). All reproducers in `tests/dbeditor_robustness/` pass.
- [x] **COL-DB-008**: When the Edit Columns dialog is confirmed, the system shall reconcile the "_all" view to contain exactly the database's current columns in position order — creating the view if it is missing, adding entries for columns it lacks, removing entries for columns that no longer exist, and renumbering its positions contiguously from zero. Implemented as `Database::reconcileAllView`, invoked from `DBEditor::applyChanges` after the column mutations.
- [x] **COL-DB-009**: When loading a view whose column list references a column that does not exist in the database, the system shall omit that reference from the loaded view rather than crashing.
- [x] **COL-DB-010**: When recalculating a calculated column's values, the system shall address each data row by its actual row ID rather than assuming row IDs are consecutive from zero, so that recalculation succeeds without crashing on a file whose row IDs contain gaps or duplicates. This was the confirmed root cause of the originally-reported add-column crash: `calculateAll` passed a physical row index to `getRow`, which treats it as a row ID, so on a file with an existing calculated column and non-consecutive row IDs the lookup missed and crashed during `applyChanges`. Fixed by looking up the row ID at each physical position; verified against the real crashing file (`summer_camps.pob`).
