# Integrity-Check Code Review Followups

Findings from a multi-pass review of `src/integritycheck.{h,cpp}` (1544 lines) run 2026-08-18: two `thermos` passes (bugs, code quality), four `qt-cpp-review` agents (ownership, API correctness, error handling, performance), and `/code-review` over the whole working diff. Line numbers are as of that date and will drift once any of this lands.

Each item records how many independent reviewers raised it — convergence is the best available signal of severity here — and whether it was verified against source rather than taken on report. Nothing below has been fixed.

## Tier 1 — The Checker Reports Healthy Files as Damaged

Both verified on both sides. These outrank everything else: a diagnostic tool that cries wolf destroys the trust the whole design rests on, and both are invisible to the 101-test suite because no fixture exercises them.

- **`CHK-DATA-004` flags every empty enum cell** (`integritycheck.cpp:881`). An empty enum value is normal and PortaBase writes it itself: `Database::addColumn` (`database.cpp:799`) does `options.indexOf(defaultVal)` on a blank default, storing `""` and `-1` into every existing row. The checker's own `checkDefault` (`integritycheck.cpp:759`) already accepts `column.defaultVal.isEmpty()` for enums, so the data-level check contradicts the column-level one. Adding an enum column with a blank default to a 200-row database yields three warnings plus "197 more rows have the same problem", exit code 1, on an uncorrupted file. Fix: exempt the empty value, matching `checkDefault`. Needs a fixture with a blank enum cell — `testfixtures.cpp` currently fills every row with `"Open"`/`"Closed"`.

- **`CHK-CORE-007` runs on pre-v4 files, which are legitimately Latin-1.** `checkUtf8Everywhere()` is called bare at `runCatalog`'s end (`integritycheck.cpp:599`) — the only check in the catalog with no version gate. Version 4 "Changed the text encoding from Latin-1 to UTF-8" (`format.md`, Version 4). A v1-3 file with any non-ASCII text warns per string per row for storing exactly what its format mandates. This also contradicts CHK-CORE-003, the project's own version-gating rule. Fix cascades from the EARS doc: CHK-CORE-007's spec line carries no version qualifier. Related: `readColumns` (`:650`, `:652`) also decodes UTF-8 unconditionally, so a pre-v4 file's non-ASCII column names become U+FFFD in finding messages.

## Tier 2 — Wrong or Missing Results

- **Property reads are never type-checked** (2 reviewers, verified). `propPresent` (`:423-426`) compares names only, discarding the type `parseDescription` already parsed. Metakit interns properties by name alone, case-insensitively (`metakit/src/view.cpp:1090-1125`), so `c4_IntProp("_gversion")` binds happily to a `_gversion:S` column. The only guard is `d4_assert`, which is plain `assert` (`metakit/src/header.h:153`) compiled out by `CONFIG += release` (`common.pri:192,226,341`) — and `q4_CHECK` is defined nowhere in this build, so every Metakit internal assert is a no-op in every configuration. `c4_IntRef::operator t4_i32` (`metakit/src/viewx.cpp:402-409`) then reads 4 bytes from whatever buffer exists. A mistyped `_gversion` yields a garbage version that drives every `versionAtLeast()` gate. The type is in hand; it is discarded at the `propPresent` boundary. A name-present-but-wrong-type property deserves its own finding.

- **The declared version is trusted absolutely.** `CHK-GLOBAL-002` catches an out-of-range version and `versionAtLeast` clamps it, but an in-range *wrong* version gates nearly the whole catalog. Empirically (2026-08-18): forcing `_gversion` from 11 to 1 on a real file suppressed `checkEnums`, `checkSortings`, `checkFilters`, `checkCalcs` and most of `checkData`, **recorded no skip notices for any of them**, and produced two bogus `CHK-COL-004` errors describing healthy enum columns as having unknown type codes. Note the reported behavior is misleading output, *not* the silent "Clean" verdict one review predicted — that stronger claim did not reproduce. `checkMandatoryViews` (`:607-631`) only checks that required views are present; it never checks the inverse, so views that entered the format at version N sitting in a file claiming version < N go unremarked even though the contradiction is visible in the parsed description. Fix: corroborate the declared version against the structural floor implied by what the file actually contains.

- **`CHK-GLOBAL-004`/`005` are dead whenever `_views` is absent** (verified). Both `_global` pointer checks live inside `checkViews` (`:958-976`), which `runCatalog` calls only under `if (viewPresent("_views"))` (`:593`). They depend on `_sorts`/`_filters`, not `_views`, and those already ran. A file that lost `_views` gets one `CHK-CORE-008` error and no word about a dangling current-sorting pointer, with no skip recorded. Fix: lift them into their own step gated on the views they actually need.

- **`haveIds` false produces a storm of bogus errors and never names the real defect** (2 reviewers). `haveIds` is computed identically at `:645` and `:672`; when false, `readColumns` sets every `column.id = -1`. But `checkData`'s guard at `:822` tests only the version, so `expectedDataProps` yields `_S-1`/`_I-1`/`_F-1` for every column — N false `CHK-DATA-001` errors, plus a `CHK-DATA-002` per genuine stored property, plus `CHK-CALC-001` noise. `columnIdsUnique` stays true (the uniqueness check is inside `if (haveIds)`), so no skip is recorded either. The actual defect — a mandatory property missing from a mandatory view — is reported by nothing, because `CHK-CORE-008` checks views only. Hoist `haveIds` to a member so the two computations cannot drift.

- **`_gcrypt` is not validated to 0/1** (3 reviewers). `:492` tests `== 1`; `Database` (`database.cpp:113`) treats any nonzero value as encrypted. A healthy encrypted file whose flag is corrupted to 2 gets the full plaintext catalog: `CHK-GLOBAL-006` fires with a message asserting `_gcrypt` is 0 when it is 2, plus `CHK-CORE-008` for every mandatory view the encrypted container legitimately lacks, and `encryptedSkipped` stays false so the explanatory note is omitted. The inverse (0 corrupted to 1 on a plaintext file) suppresses the entire real catalog while the report explains that contents were not checked. The file already range-checks `_scdesc` (`:1096`) and `_fccase` (`:1181`) this way. Note CHK-CORE-004's spec text says "`_gcrypt` = 1", so the spec needs a decision too.

- **`_vfilter` is read under `_vsort`'s presence guard** (`:930-945`). A `_views` view that kept `_vsort` but lost `_vfilter` reads an empty string, which passes both clauses of `filter != "_none" && !filterNames.contains(filter)` — so **every view** gets a spurious `CHK-VIEW-007` error. The converse ordering skips the filter check silently. Underlying issue: the empty string serves as both "property absent" and "legitimately empty" throughout this file.

- **Skip records are incomplete, so the report overstates coverage.** `checkData`'s three early returns (`:822-834`) abandon four checks and disclose two — `CHK-DATA-004`/`005` vanish silently. Those are the enum consistency checks that found the real-world `COL-DB-010` corruption. Same shape at `:866-868` and at every `viewPresent()` gate in `runCatalog`. Fix: derive each early return's abandoned set from one table mapping checks to prerequisites, so a new check cannot forget to register its skip.

- **String reads truncate at embedded NULs** (3 reviewers). `:1377` uses `QByteArray(const char*)`, which is `strlen`-based, while Metakit stores an explicit length and permits embedded NULs. `CHK-CORE-007` — the one check that sweeps every string — is blind to invalid bytes past a NUL. The same idiom appears at roughly a dozen other read sites. `c4_FormatS::Get` guarantees termination only via a compiled-out `d4_assert`, and `c4_Column::FetchBytes` can return a raw pointer into the mapped file, so a damaged length also sends `strlen` off the end. Fix: `c4_View::GetItem(row, col, c4_Bytes&)` yields an explicitly sized buffer; `QByteArray(ptr, size)` closes both the false negative and the over-read.

- **Duplicate `_eoindex` values silently drop an enum option** (2 reviewers). `:1269` inserts into a `QMap<int, QString>` keyed on the raw file value, so a repeat overwrites. `CHK-ENUM-004` reports the collision, but `CHK-DATA-004` then reports every row using the dropped option as "not an option of this column's enum" — findings pointing at intact data — with no `addSkip` linking them, even though CHK-CORE-005 exists for exactly this. Duplicate `_eid` values have the same shape one level up: two enums' options merge, so `CHK-DATA-004` validates against a union and a genuinely invalid value can pass.

- **`Scan::storage` dangles on both early-return paths** (3 reviewers, verified). `:457` points a member at a stack local; `:501` clears it only on the success path, so the `Unreadable` returns at `:463` and `:468` leave it pointing at a destroyed object. No live dereference today — the constructor reads only the result fields — but those are exactly the paths a corrupt file takes, and any future post-`run()` work would read freed stack. `Scan` is also implicitly copyable while holding a non-owning pointer.

## Tier 3 — Unbounded Growth

Raised by **all four** reviewers, the strongest convergence in the set.

- **`addRowViolation` retains every violation to print three.** `:360-377` fully constructs a `Finding` (three `QString`s, two `arg()` formats) and appends unconditionally; `flushRowViolations` (`:384-403`) then emits at most `ROW_REPORT_LIMIT` and discards the rest. `Finding` carries no `Q_DECLARE_TYPEINFO`, so Qt 5's `QList` heap-allocates each element separately. A 1M-row file with a mangled string column retains hundreds of MB to print four lines. Fix: cap at collect time, keeping an `int` counter instead of the discarded majority; `flushRowViolations` builds its aggregate from the counter. The existing `perRowFindingsAreAggregated` test should pass unchanged.

- **~18 of ~22 per-row checks bypass the aggregation mechanism entirely**, calling `addFinding` directly from row loops with no cap: `:922`, `:933`, `:940`, `:1001`, `:1006`, `:1062`, `:1086`, `:1091`, `:1097`, `:1130`, `:1161`, `:1168`, `:1175`, `:1182`, `:1225`, `:1230`, `:1235`, `:1263`, `:1314`, `:1344`, `:1352`. The sharpest evidence it is an oversight: within one loop over `_calcnodes`, `CHK-CALC-003` (`:1336`) aggregates while `CHK-CALC-004`/`005` (`:1344`, `:1352`) do not. `commandline.cpp:360` materializes the whole report into one `QString` before printing, so a pathological file OOMs before emitting a single line — the exact opposite of the tool's purpose.

- **Position maps are keyed on file-derived strings**, amplifying the above: `positionsByView` (`:990`) creates one map entry per row when owner names are garbled, and `isPermutation([x])` is false unless `x == 0`, adding a third finding per row. Same at `:1077`, `:1152`, `:1255-1256`. Key aggregation on the check ID rather than the owner string.

Widening CHK-CORE-006 from "over `_data`" to "over any view's rows" is a prerequisite spec edit — the code already applies the mechanism beyond `_data` at `:1336` and `:1379`.

## Tier 4 — Simplification (~250 lines)

Ordered by reduction per unit of risk.

- **The public API costs ~85 lines to expose 5 fields** (`:1391-1471`). Six accessors, each with a mandated Doxygen block, over fields declared twice — once in `Scan` (`:292-296`), once in `IntegrityCheck` (`integritycheck.h:76-81`) — and copied field-by-field at `:1405-1409`. Give both sides one shared `Result` struct with trailing `/**< … */` member docs: ~5 lines instead of ~85. **Do not merge `Scan` into `IntegrityCheck`** — that split is load-bearing, since `Scan` holds `c4_Storage*` and pulling `mk4.h` into the header would break the QtCore-only decoupling. Cost is ~20 call-site edits in the tests and 2 in `commandline.cpp`.

- **`filePath()` (`:1417-1420`) has zero callers** anywhere in `src/` or `tests/` (verified). `report()` uses the `path` member directly. −13 lines.

- **Four repeated mechanisms, ~−63 lines.** The permutation-by-owner block appears verbatim four times (`:1015-1023`, `:1103-1111`, `:1192-1200`, `:1272-1280`) plus two single-list near-copies (`:720-725`, `:1243-1247`); keying the accumulator by the finished location string collapses all of them, including the int-keyed enum one, and deletes `indexesByEnum` as a separate map. Name-uniqueness collection appears four times (`:918-926`, `:1058-1067`, `:1126-1135`, `:1219-1228`) — note the severity differs, CHK-ENUM-001 is an Error where the others are Warnings. The three `_global` pointer checks (`:948-976`) are one shape three times, and lifting them also stops `c4_View &global` being threaded through two frames. The "references a column that does not exist" test appears at `:1005`, `:1090`, `:1167`.

- **The type-to-storage-letter mapping exists three times** (3 reviewers, verified). `expectedDataProps` (`:254-283`) re-derives what `Database::makeColId` (`database.cpp:2358-2377`) and `Database::formatString` (`database.cpp:2402-2423`) each encode independently — and those two already duplicate each other. `makeColId` is a `private static` pure function touching no instance state, so **making it public static is the cleanest fix** and avoids the `Database` construction the design doc forbids; `formatString` genuinely cannot be reused (non-static, reads the live `columns` view). Separately `:864-865` derives `"_S" + id` / `"_I" + id` by hand a fourth time rather than calling `expectedDataProps`. −30 lines and a real drift hazard removed. `formatString` is inside the declared LID scope, so this cascade is in-segment.

- **`boundedRuns` is a strict superset of `boundedList`** — a list with no consecutive runs formats identically, and run-collapsing is equally desirable for the `duplicated` and `missing` lists. Delete `boundedList`, route all three through `boundedRuns`. −15 lines, one test assertion to re-check. Both also carry their own unnamed `const int limit = 8` (`:61`, `:83`) in a file that already has a documented `ROW_REPORT_LIMIT`.

- **Magic numbers shadow constants that already exist** (3 reviewers). `expectedDataProps` (`:258-263`) and `checkDefault` (`:747-748`) case on `1`/`3`/`5`/`6`/`8` with explanatory comments, in the same `switch` as `case FLOAT:`/`case IMAGE:` — `datatypes.h` defines `INTEGER`, `BOOLEAN`, `DATE`, `TIME`, `SEQUENCE` and is already included. `:1174` uses `op < 0 || op > 7` where `Condition::Operator` (`src/condition.h:35-44`) runs `Equals = 0` … `NotEqual = 7`. `:1342` uses `type == 1 || type == 3 || type == 5` where `CalcNode::Column`/`DateColumn`/`TimeColumn` exist, and `:1349-1350` hardcodes `20`/`34` where `CALC_FIRST_OP`/`CALC_LAST_OP` are `#define`d for exactly this (`src/calc/calcnode.h:19-20`) — so adding a 35th operation silently makes the checker flag every valid new node. `calcnode.h` and `condition.h` are leaf headers; the "don't reuse Database" rationale does not extend to them. The comments delete themselves once the constants are used.

- **`Scan` is a 1100-line struct with every method inline** (`:289-1387`). There is currently nowhere a reader can see the list of checks the engine runs. Declaring it normally (members plus method declarations, ~40 lines) and defining methods out-of-line costs zero behavior risk, matches every other file in `src/`, and is probably the largest comprehensibility gain available. `checkViews` (`:908-1045`, 138 lines) does five distinct jobs and should split regardless.

- **`parseDescription`/`splitTopLevel` (`:186-238`) reimplement Metakit's own structural API.** `c4_Storage` derives from `c4_View`, so `NumProperties()`/`NthProperty(i).Name()` enumerates top-level views without mutation — verified against a real file. Their consumers `propPresent` (`:423-426`) and `stringProps` (`:434-444`) likewise re-derive what `c4_View::FindPropIndexByName()` and `c4_Property::Type()` provide, and `propPresent` currently allocates a whole `QStringList` of every property name per call, at ~25 call sites. **Caveat: `FindPropIndexByName` matches case-insensitively** while the current name comparison is case-sensitive, so the swap is a behavior change for a file with, say, a `_GVERSION` property — decide deliberately. This refactor also carries the Tier 2 type-check fix, since `Type()` becomes free.

- **Quadratic scans.** `checkData`'s `stored.contains(prop)` / `expected.contains(prop)` (`:841-857`) are O(columns²) — ~250k string comparisons on a 300-column database. `columnNames.contains(colName)` inside the `_viewcolumns`/`_sortcolumns`/`_filterconditions` loops (`:1005`, `:1090`, `:1167`) is O(columns × child rows). The file already uses `QSet` for `seenIds`/`seenNames`, so the idiom is established. Zero net lines.

- **`Scan::allViewPresent` (`:306`) is member state with purely local lifetime** — set at `:981`, read at `:1025`, both inside `checkViews`. Its three siblings are genuinely cross-method. Make it a local.

### Measured and Rejected

**Collapsing the ~10 near-parallel `check*` methods into a table-driven driver is not worth it.** Two reviewers measured it independently: ~35 lines saved by one estimate, ~60-90 out of 667 by the other. The build is pinned to C++11 (`common.pri:226-227`), so with no designated initializers each table literal costs 10-11 lines and gives back what the loop saved, while pushing 20+ spec IDs, severities and message strings behind a generic driver. The descriptor does cover all five parent/child view pairs, but the shared skeleton is only ~45% of those lines; the residue (`_vsort`/`_vfilter` defaults, `_all` ordering, `_scdesc`, `_fcoperator`, enum ID ranges, calc node types) stays as five callbacks. The methods are the readable part; the mechanisms inside them are the noise, which is what the Tier 4 helper extractions target instead.

### Splitting the File

Not yet. Tier 4 lands it around 1150-1200 lines, and the out-of-line `Scan` declaration makes those far easier to navigate without moving any of them. If it is still uncomfortable afterwards, follow the design doc's own architecture split rather than the invariant-catalog grouping: `integritycheck.{h,cpp}` for the value types and `exitCode()` (QtCore only, ~120 lines); an internal scan engine header that may include `mk4.h` (~350 lines); one catalog translation unit ordered to match the design doc (~650 lines). Splitting the catalog further is counterproductive — those checks share `Scan` state heavily and scattering them hides the coupling.

## Arrow-Level Corrections

These need spec edits, not just code changes.

- **The missing-`_id` finding is filed under the wrong check ID.** `:816` reports `CHK-DATA-001` from a block annotated `@spec CHK-DATA-003`. CHK-DATA-001 covers "each data property required by the column set (per the format's column-ID derivation rules)" — `_id` is structural, not column-derived — and CHK-DATA-003 covers `_id` *values*, not the property's presence. Neither covers this case. Check IDs are public contract: the CLI prints them and the tests assert on them.
- **CHK-DATA-005's spec is wrong and the code is right.** The spec says the stored index should equal the option's `_eoindex`; the application stores a *position* — `Database::listEnumOptions` (`database.cpp:1847-1857`) sorts by `_eoindex` and returns a positional list, and `database.cpp:1535` stores `options.indexOf(value)`. Reword to "position among the enum's options ordered by `_eoindex`".
- **CHK-CORE-006 is scoped to `_data`** but the mechanism is already applied to `_calcnodes` (`:1336`) and every view (`:1379`). Widen it.
- **CHK-CORE-007 needs a version qualifier** (Tier 1).
- **CHK-CORE-004 says `_gcrypt` = 1** where the application's rule is `!= 0`.
- **No mandatory-*property* check exists.** `CHK-CORE-008` validates view presence only. A `_columns` view that lost `_ctype` yields type 0 for every column, which passes the `0 <= type <= LAST_TYPE` test, so an all-string-column database reports Clean. Worth deciding whether this is a spec gap or intentional.

## Known Non-Findings

Recorded so they are not re-audited: no `Find()` call sites exist in this file, so the unguarded-`Find` crash class does not apply. All 15 `storage->View(...)` sites are correctly guarded by `viewPresent()` first — load-bearing, since `c4_Storage::View` creates on access (`metakit/src/store.cpp:245`). Read-only is enforced at the OS level (`fopen(..., "rb")`, `metakit/src/fileio.cpp:331`, no `Commit()`). `isPermutation`'s bitset is sized by value count, not largest value, so a hostile ID cannot drive an allocation. `qAsConst` is applied at all six member-container range-for sites. `QMap` iteration order is deliberately load-bearing at `:1038` and `:1283`, not a nondeterminism risk. `exitCode`'s precedence is correct.

## Open Investigation

- **Metakit's loader is entered before any PortaBase guard runs**, with all consistency checks disabled. Row counts come straight from the file (`metakit/src/handler.cpp:316-318`) with no cross-check against file size, and `q4_CHECK` is defined nowhere so every `d4_assert` is a no-op. An inflated row count in a `:B`/`:S` column allocates from the file's claim and can read out of bounds; `:I` columns degrade to silent zeros instead. `CHK-CORE-002` promises "without crashing", which is guaranteed only above the loader. Needs a raw byte-patching helper in `PobCorrupt` (it currently mutates through the Metakit API, so it cannot forge a bad row count) and an ASan run to characterize. Mitigations if confirmed: a pre-flight bound from the file's byte size, and either a fork-per-file scan or a fault handler converting a crash into `Unreadable`. Defining `q4_CHECK` is not a fix — it turns no-op asserts into `abort()`.
- **`checkUtf8Everywhere` is the dominant cost on clean files**, contradicting the HLD tenet added 2026-08-06. It re-reads every string `checkData` already walked and does three allocations per string per row. A hand-rolled validator would fix it but *adds* ~20 lines, so it loses on the reduction axis.
- **Public structs lack member initializers** (`integritycheck.h:50-61`). A default-constructed `Finding` holds an indeterminate `Severity`. No live defect — every construction site sets all fields — but `Scan` already uses NSDMIs, so the file has committed to the idiom.
- **Six anonymous-namespace helpers have doc blocks with no `@param`/`@return`** (`:52`, `:58`, `:186`, `:211`, `:239`, `:249`), while three siblings in the same file comply. CLAUDE.md requires the full block on the `.cpp` definition.
- **Three conventions coexist for passing results between phases** — pointer out-params (`checkSortings`), `Scan` members (`readColumns`), and a threaded parameter (`global`). Pick one.
- **`count` is reused for two different views within single functions** (`:917`/`:992`, `:1058`/`:1078`, `:1126`/`:1153`, `:1218`/`:1257`, `:1294`/`:1327`). Correct as written, one misplaced statement from an out-of-range loop.
- **`CHK-CORE-008`'s message prints the raw declared version** while the gate used the clamped one, so a version-99 file is told "mandatory view missing for a format version 99 file".
- **`CHK-GLOBAL-003` lacks the empty-value exemption** its two siblings have (`:948-956` vs `:958-976`), so an empty `_gview` reports `current view "" does not exist`. Plausibly intentional; collapsing the trio forces the question.
