# Column-Editing Code Review Followups

Findings from a `qt-cpp-review` deep audit of `src/dbeditor.{cpp,h}`, `src/database.{cpp,h}`, and `src/columneditor.{cpp,h}` — run while investigating the `COL-DB-007` add-column crash (see `docs/intent/column-editing/column-editing-design.md` § Open Questions & Future Decisions). None of these are the crash itself; they're real but lower-priority items surfaced along the way, deferred here rather than bundled into that investigation.

## Unguarded `c4_View::Find()` Results

About ten call sites across `database.cpp` and `dbeditor.cpp` do `int i = view.Find(...)` and immediately index `view[i]` with no check for `i == -1`:

- `database.cpp`: `setIndex` (~555), `setDefault` (~594), `renameColumn` (~885)
- `dbeditor.cpp`: `editColumn` (~188), `deleteColumn` (~305), `moveUp`/`moveDown` (~339, 342, 362, 366), `renameColumnRefs` (~629), `deleteColumnRefs` (~649)

Under the current, intended call sequences these all look safe today — nothing yet drives them with a name that isn't already known to exist. But nothing defends against it either: a `Find()` miss silently indexes the view at `-1`, which the vendored Metakit doesn't fail fast on (confirmed by reading `metakit/include/mk4.inl` and `metakit/src/column.cpp`/`viewx.cpp`) — it builds a cursor that only crashes *lazily*, the first time a property on that row is read or written, with no assert in release builds. A loaded footgun rather than an active bug, but worth guarding defensively (matching the one correct existing instance in `DBEditor::applyChanges()`, `dbeditor.cpp:513`, which does check).

## Other Investigation Targets

- **Origin of real-world non-consecutive row IDs — bulk filtered delete, ID compression did not take.** `summer_camps.pob` holds 25 rows whose `_id` values are 74-98: contiguous, ascending, no gaps or duplicates within the run. The maintainer's account of the file matches that signature exactly — it began as last year's camp options, this year's were copied and appended, then last year's were filtered for and deleted as a group. So the 74 deleted rows were the low IDs and the 25 survivors are the appended block, left at their original numbering.

  The one code path that deletes without renumbering per row is `View::deleteAllRows()` (`view.cpp:488`), which calls `Database::deleteRow(id, false)` for each row and then `Database::compressRowIds()` once at the end. Compression evidently did not take effect, or was not persisted. `compressRowIds()` (`database.cpp:1630`) writes the sort key of a derived sorted view while iterating it — `data.SortOn(Id)`, then `Id (row) = i` — which Metakit's own `SortOn` documentation (`view.cpp:420`) warns about: the result "merely maintains a permutation" tracked by change notification, "with major limitations". Hand-tracing the simple case does complete correctly, so if this is the mechanism it needs a particular filter or ordering to trigger.

  Not yet reproduced. The test is cheap: build a fixture of ~99 rows, delete a filtered subset through `View::deleteAllRows()`, and check whether the surviving IDs compress to 0..n-1. Worth doing before attempting a fix, since an unguarded `data.Find()` in `deleteRow` (see above) is an alternative candidate for the same symptom.
- **`Database::load()` assumes row IDs are consecutive** (`database.cpp`): `maxId = data.GetSize() - 1`, and `addRow` assigns `maxId + 1` as the next row's `_id`. On a file whose IDs are not a permutation of 0..n−1, the next added row can duplicate an existing `_id` — after which every `data.Find(Id[rowId])` lookup (row edit, delete, `getRow`) resolves to whichever duplicate is physically first: silent wrong-row edits and deletes. A robust `maxId` would be `max(_id) + 1` computed from the actual data. This is a *robustness* gap (mis-set `maxId` propagates a pre-existing gap into duplicates), not necessarily the original gap-writing mechanism.
- **`Database::deleteRow()` renumbers even when the row wasn't found** (`database.cpp`): `data.Find(Id[id])` is unguarded, so a request to delete a nonexistent row ID does `RemoveAt(-1)` (Metakit behavior unverified) and then *still* decrements every row ID above the missing one and `maxId` — shifting IDs with no corresponding removal. Worth guarding regardless, though the maintainer reports few deletions on the known-affected file, so this is likely not that file's origin.
- **`getRow()` index-vs-ID audit (2026-07-14): clean apart from the fixed COL-DB-010 bug.** `Database::getRow(rowId)` takes a row ID; `View::getRow(index)` takes a view position. All call sites pass the correct kind (UI paths translate view index → row ID via `View::getId(index)` before ID-based edit/delete). Stored calculated values are written through a single funnel, `Database::calculateAll(colId, root, decimals)` — the one COL-DB-010 fixed. **Still TODO** (maintainer request): a broader audit across *all* functions taking a row index or ID argument (`getId`, `getIndex`, `updateRow`, `deleteRow`, `editRow`, model↔view index mapping), for the same confusion class.
- **`Database::addColumn()`'s ID-gap-scan has no defense against a pre-existing duplicate `cId`** (`database.cpp:698-717`). The "find the next available ID" loop assumes existing `cId` values are unique; it has no assertion or check for that precondition. A duplicate (from any future corruption) would desync the scan silently.
- **`Database::commit()` discards Metakit's `bool` success/failure return** (`database.cpp:2393-2400`). `storage->Commit()`/`file->Commit()` both signal real I/O failures (disk full, write error) via their return value; `commit()` ignores both, so a failed save currently looks identical to a successful one to the caller.
- **`DBEditor::edit()` never resets staged state** (`dbeditor.cpp:99-125`). It repopulates `info`/`calcMap`/`decimalsMap`/`deletedCols` without clearing them first, so calling `edit()` twice on the same `DBEditor` instance would leak `CalcNode*` values and duplicate rows in `info`. Not reachable today — the only call site (`portabase.cpp:383`) constructs a fresh `DBEditor` per invocation — but worth hardening if the dialog is ever pooled/reused.

## From the 2026-08-18 Whole-Diff Review

Raised by `/code-review` over the full working tree, so these sit outside the integrity-check file that review pass was aimed at (see `docs/wiki/integritycheck-code-review-followups.md` for that segment, and its Remediation Plan for how these items are sequenced against it — the test-helper drift below is scheduled ahead of the rest). Line numbers are as of that date.

- **`Database::reconcileAllView` does not handle duplicate `_all` entries** (`database.cpp:1810`), so it does not meet COL-DB-008's "contain **exactly** the database's current columns … renumbering its positions contiguously from zero". If `_all` holds two `_viewcolumns` rows for the same existing column, neither loop touches them — the name is in `finalCols` so it is not deleted, and in `allCols` so it is not added — and `setViewColumnSequence` (`database.cpp:1788`) only `Find`s the first matching row, so the duplicate keeps its stale `_vcindex` and collides with another column's new index. The triggering state is exactly what `IntegrityCheck` reports as CHK-VIEW-002/CHK-VIEW-006, so the two tools describe the same defect from opposite sides.

- **`PbTest::completePostAcceptSequence` no longer mirrors `PortaBase::editColumns`** (`tests/common/dbeditordriver.cpp:99`). Production now captures `hadViews` before `applyChanges()` and then calls `viewAllColumns()` or `viewer->setDatabase(db)`, never `addView`/`setViewColumnSequence` again. The helper still runs the old pre-change sequence, and since `applyChanges()` → `reconcileAllView()` now always creates `_all`, `db->listViews()` is never empty, so the `addView` branch is dead. `postAcceptSurvivesMissingAllView` and `postAcceptSurvivesOrphanedAllEntry` (`dbeditor_robustness_test.cpp:208,223`) therefore claim to exercise the application's post-accept sequence but exercise one the application no longer has — a regression in the new `hadViews` branch would not be caught. The helper's doc block (lines 92-98) also still describes the old code. **Two passing tests giving false confidence, which is worse than a failing test**, and worth fixing before relying on this suite as the safety net for other work.

- **`CommandLine::checkFiles` returns 2 for a usage error** (`commandline.cpp:355`) — invoking `portabase check` with no file paths. Per CHK-CLI-004 and the usage text, exit code 2 means "a file was unreadable / not a PortaBase file", and every other CLI usage error in `process()` returns 1 (`commandline.cpp:64`). A script branching on `$? == 2` to mean "corrupt file" misreads a missing-argument invocation.

- **`database.cpp:268` still does `views[index]` without checking `Find` for -1**, in the same function where the COL-DB-009 guard was added three lines below. `IntegrityCheck`'s CHK-GLOBAL-003 implies files exist in the wild where `_gview` names a missing view. Belongs with the unguarded-`Find` cluster at the top of this document.

## Lint Findings (Style/Modernization)

`mise run lint-cpp` (cppcheck, via `prek.toml`'s `lint-cpp` hook) now runs automatically against new/changed C++ files on every commit — but that only covers files touched going forward, not retroactively. Running the full `qt_review_lint.py` deterministic linter (from the `qt-cpp-review` skill) against the reviewed files surfaced ~35 pre-existing findings, none crash-related, all cheap fixes whenever these files are next touched substantively:

- **`DEP-10` (.count()/.length() → .size())** — ~20 call sites, mostly in `database.cpp`, a few in `dbeditor.cpp`. Pure style; `.count()`/`.length()` and `.size()` are equivalent on Qt containers.
- **`API-5` (get-prefix on plain getters)** — ~11 call sites, mostly in `database.h` (`getIndex`, `getType`, `getDefault`, etc.), one in `dbeditor.h`. Qt convention reserves the `get` prefix for user-interaction/decomposition getters; a rename would be a real API-shape change across every caller, so lower priority than the others here.
- **`PAT-7` (`QMap` usage)** — 2 sites in `dbeditor.h` (`NameCalcMap`, `NameDecimalsMap` typedefs). Flagged as "verify copying is needed; `std::map` saves ~1.7KiB text" — worth a look, not urgent.
- **`ENM-2` (unscoped enum without explicit underlying type)** — 1 site, `database.h:45` (`Database::OpenResult`). Adding an explicit underlying type would help binary compatibility if this enum's values are ever persisted/exchanged externally.
- **`DEP-13` (`QChar` as object type)** — 1 site, `columneditor.cpp:242`.

## Build/Test Infrastructure Followups

- **Tooling bugs found in this project are documented but not yet filed upstream** (as of 2026-08-04). `docs/wiki/mdbook-lint-bugs.md` holds six (#1-#5 plus #3a), `docs/wiki/rumdl-bugs.md` one, and `docs/wiki/compiledb-bugs.md` and `docs/wiki/cppcheck-bugs.md` predate them. Each entry is written as draft material for an upstream issue, with a root cause and a reproduction; several note that no exhaustive search for an existing issue was done, which is the first step before filing. The mdbook-lint code-span-blindness items (#3a and #5) share one root cause and are worth filing as a single report.
- **`lint_cpp.py` doesn't run clang-tidy/clazy.** They need a compile database, and the test suite currently recompiles the same shared sources as the app with different flags — revisit alongside splitting the shared sources into a library target both link against (see `docs/wiki/compiledb-bugs.md` for a compiledb defect worth re-checking then).
- **The test targets link the whole application, not their actual dependency closure.** `tests/dbeditor/dbeditor_test.pro` pulls in all ~170 shared sources via `common.pri` to exercise `DBEditor`. Deliberately deferred rather than overlooked (maintainer intent as of 2026-07-13): there is no existing internal library boundary to link against, and hand-curating one now would drift stale as the codebase evolves. Revisit once the roadmap's UI/logic split produces a real module boundary — the same boundary the clang-tidy/clazy item above is waiting on.
- **cppcheck's flag set is triplicated** across `packaging/cppcheck/cppcheck.sh`, `cppcheck.bat`, and `lint_cpp.py`'s `run_cppcheck()` — the same `--enable=all --inconclusive --library=qt --suppressions-list=...` core, defined three times. A future flag change only gets applied wherever someone remembers to edit it. Worth consolidating (e.g. `lint_cpp.py` shelling out to `cppcheck.sh` with an extra file-list argument, or extracting the shared flags to one config file) — plausibly worth doing alongside a comparative evaluation of other C++ linters (maintainer intent as of 2026-07-14, not yet scheduled).
- **`mk4.h`/`mk4.inl`/`mk4str.h`/`mk4str.inl` are manually copied into `build/` and `tests/dbeditor/build/`, not make-tracked.** `qmake portabase.pro && make` needs these present in the build directory (the `-Ibuild` include path resolves them) but nothing in the generated Makefiles actually places them there — `debian/rules` copies them as an explicit packaging step (`cp metakit/include/mk4.h metakit/include/mk4.inl metakit/include/mk4str.h metakit/include/mk4str.inl build/`), which the plain `qmake && make` flow documented in `CLAUDE.md`/`doc/install_linux.txt` never runs. Because the copy isn't a make-generated artifact, neither `make clean` nor `make distclean` removes it — a full reset of either build directory needs a manual `rm -rf`. Worth either making this copy step part of the qmake project itself (a `QMAKE_POST_LINK`-style pre-build copy, or a documented one-time setup step) so it's both automatic and properly clean-tracked.
- **Docstring linting (Doxygen) — not yet wired up** (maintainer intent as of 2026-07-19, not yet scheduled; deliberately deferred out of the commit that documented the docstring convention in `CLAUDE.md`). Doxygen's own warnings are the C++ "docstring linter": on a lint config with `EXTRACT_ALL = NO` (the root `Doxyfile` currently has `EXTRACT_ALL = YES`, which *suppresses* undocumented-warnings) plus `WARN_IF_UNDOCUMENTED`, `WARN_IF_DOC_ERROR`, `WARN_IF_INCOMPLETE_DOC`, and `WARN_AS_ERROR = FAIL_ON_WARNINGS`, it flags undocumented functions/params/members and `@param` mismatches. Two caveats: (1) it will *not* enforce this repo's `.cpp`-vs-`.h` docstring **placement** rule (Doxygen is placement-agnostic) — that needs a small custom check (in `.h` files, flag a `/**` block, not `/**<`, immediately before a function declaration; no backlog since the current headers are clean), foldable into `packaging/lint_cpp.py`; (2) flipping `EXTRACT_ALL` off over the whole ~25-year-old `src/` tree will surface a large pre-existing undocumented backlog, and Doxygen doesn't cleanly lint only-changed-files (it needs the whole tree for cross-references). Suggested path: add `doxygen` to `mise.toml`, run it once to *size the backlog*, then decide hard-gate vs. "warnings must not increase" baseline; add the placement check to `lint_cpp.py` independently (it's ready now). Wire the result into the `prek` hooks and the routine agent lint pass. Plausibly bundle with the clang-tidy/clazy and cppcheck-consolidation items above.
- **The per-type add-column test slots are collapsible boilerplate.** `tests/dbeditor/dbeditor_test.cpp` has nine near-identical `addColumn_STRING`/`addColumn_INTEGER`/etc. slots that a QtTest `_data()`-driven table would reduce to one pair (raised by a code-quality review, 2026-07-13). Low priority — the duplication is legible and harmless — but worth folding in whenever those tests are next touched.
- **`packaging/lint_cpp.py` doesn't separate file-path arguments with `--`.** Defensive only: nothing there uses `shell=True`, so there is no injection path today. Worth adding if the argument construction ever grows more dynamic.
